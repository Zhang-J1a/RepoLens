# V1.3 逐题审阅与子查询融合实验

## 结论

暂时保留 V1.3 默认检索，子查询融合实验不进入默认路径。V1.3 的 Recall@10 相比 V1.2 有 6 题改善、3 题回退、21 题不变；融合实验找回了两道题的测试证据，但整体指标下降，并新增两道零命中题，未通过预设门槛。

这 30 题已用于 V1.3 权重选择和诊断，属于开发集。它们不能同时充当独立测试集，分数提升不代表跨仓库泛化。后续先建立未参与调参的验证集，再考虑修改默认策略。

## 可复现范围

- 数据集：`eval/flask-questions.jsonl`，30 题、63 条 locator。
- Dataset SHA-256：`77cfaea4a405c21716583ad9498715b28ab0b6b2278924eca843b3715503cd37`。
- Flask commit：`d086db856be187255b8ec61ef409357393020f32`。
- 索引策略：`git-objects-v1_ast-md-atx_lines80-overlap15`；数据库仅含这个 Flask snapshot。
- 保存的基线：`eval/flask-baseline.json`、`eval/flask-v1.3-baseline.json`，均保持原样。
- 审阅产物：`eval/flask-v1.3-review.json`，包含所有题目的四项指标、各 gold 在候选/最终列表的排名、各路径的 top-10 定位、子查询和源码 hash。产物不包含上游源码正文。

脚本还原 V1.2 的普通词 OR 查询，V1.3 则调用当前 `match_expression` 一次。逐题核对两版四项指标及覆盖数与保存基线一致，并验证当前 top-10 evidence ID 顺序与 `search` 相同；任何不一致都会中止。历史基线未保存排名，故历史排名是由冻结的算法重放得到，不是对历史 top-10 文件的直接核对。

此前临时诊断中出现过“在 V1.3 查询上再次追加短语”的写法，它会改变 BM25 权重。这样的诊断结果不用于本报告。正式回放的两版分数与保存基线一致。

## 回退与未命中的原因

排名按“V1.2 原始 BM25 → V1.3 短语扩展后的 BM25 → V1.3 重排”列出。范围是前 100 个候选；未找到不代表证据未被索引。

| 题号 | 证据 | 排名变化 | 诊断 |
|---|---|---|---|
| 012 | `App.add_url_rule` | 10 → 14 → 40 | 跨类调用证据回退。查询含 `BlueprintSetupState.add_url_rule`，目标却是 `App.add_url_rule`；覆盖特征只命中 `endpoint`。短语扩展和重排都影响排名。这里两条 gold 都是实现方法，不是实现加测试。 |
| 014 | `test_unique_blueprint_names` | 2 → 2 → 30 | 纯重排回退。模板回调等 `Blueprint.*` symbol 获得 3 分前缀加分，测试没有；两者都覆盖 `blueprint/name`，加分足以颠倒顺序。 |
| 028 | `test_session_transactions` | 5 → 5 → 15 | 纯重排回退。测试覆盖 `session/client`，cookie 相关候选再多命中 `cookie` 获得 4 分，挤掉正确测试。 |
| 023 | `AppContext._get_session` | 4 → 4 → 7 | R@5 回退但 R@10 不变。`match_request` 是 24 → 24 → 25，仍在候选池。这里三条 gold 都是实现方法，没有测试证据。 |
| 010 | `test_response_types` | 3 → 7 → 4 | Recall 不变，第二条证据变晚，nDCG 小幅回退。 |
| 006 | `Flask.process_response` / `finalize_request` | 30 → 34 → 9 / 50 → 51 → 29 | 部分改善，短小嵌套回调占据前三，完整生命周期证据仍靠后。 |
| 027 | `test_test_client_context_binding` | 20 → 21 → 63 | 精确的 `Flask.test_client` 被提至第一，但测试只调用 `app.test_client`，无法获得同等 qualified-name 覆盖。 |
| 015、029 | `_check_setup_finished` / `test_async_route` | 均未进入两版前 100 | 候选召回不足；仅重排前 100 无法解决。 |

`identifier_terms` 会提取普通英文词，覆盖率使用子串检查；这些只是词法信号，并不证明代码调用关系。当前 symbol root 也是名称前缀，不是经解析器验证的继承/调用边。短语查询交给 SQLite `unicode61` 分词，例如 `add_url_rule` 会变成相邻词约束，并非精确标识符相等。

## 标注局限

保持数据集 hash 不变，并将以下事项留给独立数据审阅：

- 多数题同时标注实现和测试，但原问题未必要求测试。当前 Recall 要求覆盖全部已标注 locator，分数不是答案正确率。
- 010 的 `make_response` 1289-1303 行只覆盖 tuple 解包，不覆盖 dict/list 转 JSON 的实现；路径可解析不等于语义证据充分。
- 013 的真值 338-377 行与上一块 273-352 行有交集，因此只找到重叠前缀也可能得分。当前“相交即命中”不保证整个行为已被召回。
- 没有未标注候选的人工相关性判断，也没有纯中文无标识符问题、不可回答题和独立仓库测试，不能据此评价答案生成或拒答。

## 融合实验与决策

独立脚本位于 `experiments/retrieval_review.py`，不随 `src` package 安装。原查询使用 V1.3 排名；从原问题中选取最多三条含 `_` 或 `.` 的显式代码名，可加入 qualified name 的末段。子查询执行字面短语 FTS 检索，每路最多 100 个候选。各路按 `1/(60+rank)` 等权 RRF 相加；每条路相同 evidence ID 只贡献一次，最后按 ID 去重。融合后不再把不同查询的 BM25 分数相加，也不再重排。

这只是标识符拆分，不是语义问题拆解，不会根据 gold、预期答案或测试文件名生成子查询。30 题的查询次数分布：4 题一次、9 题两次、11 题三次、6 题四次，共 79 次 FTS 查询（不含审阅用的重放和校验）。

运行前的门槛：R@10 必须提高，四项宏平均均不得下降，不得新增零命中题。实际 R@10 有 2 题改善、5 题回退，005 和 006 新增零命中。027 的测试排名从 63 回到 10，028 从 15 回到 4；但重复聚焦显式代码名让完整自然语言中的行为条件变弱，例如 005 的 `preprocess_request` 从 1 降到 12。

**决策：保留实验及负结果用于复现，不替换默认 V1.3，不继续在这 30 题上搜索融合权重。** 先增加独立验证集，覆盖自然语言、精确符号、跨方法证据和无证据场景；然后针对前缀加分、子串覆盖等明确问题做窄范围修复，按独立结果决定是否发布。DeepSeek 的生成接入仍留在 V2。

## 复现命令

在项目根目录执行：

~~~powershell
$env:PYTHONPATH = "src"
python -m experiments.retrieval_review eval/flask-questions.jsonl --snapshot snapshot_d157332a493291d8065f3d78825454f7479f8f6c8cbc9ea5bcb25f818a756656 --data-dir data/index --v12 eval/flask-baseline.json --v13 eval/flask-v1.3-baseline.json
~~~

输出 JSON 到 stdout。更换本地 clone 会改变 snapshot ID；该脚本拒绝把不同 snapshot 或不同数据集与已有基线混比。若要在另一 clone 上重建实验，需要先生成对应的固定基线。所有目标仓库操作只读，实验不联网、不需要 API key。
